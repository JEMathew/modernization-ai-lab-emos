# ADR-0001: Canonical 6R Recommendation Boundary

## Context

The existing assessment engine deterministically emits six legacy labels and
persists evidence snapshots, criterion results, findings, and trust health. It
does not persist a canonical recommendation object or alternative reasoning.
The new object changes a public artifact and SQLite schema, while the product
must preserve the distinction between recommendation, decision, and execution.

Verified facts are that `engine.workflow.run_assessment` owns the current
assessment operation, `AssessmentRun` owns its immutable run bundle, and the
local `TrustedAssessmentStore` persists that bundle transactionally. Production
authorization, tenant enforcement, and durable execution are not implemented.

## Decision drivers

- Make 6R recommendations traceable and challengeable.
- Preserve deterministic numeric authority and evidence provenance.
- Avoid a parallel source of truth or an LLM-owned decision boundary.
- Keep the existing Apex scores and DataFrame API compatible.
- Fail closed at the recommendation-to-execution boundary.

## Considered options

### Option A — Add recommendation records to the assessment-run aggregate

Extend the existing strict models and transactional bundle. This reuses the
authoritative snapshot, findings, trust evaluation, workflow, artifact, and
store, with a small additive schema change.

### Option B — Create a separate recommendation service and database

This could isolate future scale but would duplicate current workflow ownership,
introduce synchronization and failure modes, and exceed the local slice.

### Option C — Keep recommendation detail in Streamlit session state

This is reversible but not durable, versioned, or auditable, and would make the
UI an unauthorized source of truth.

## Decision

Select Option A.

- `ModernizationStrategy` is the canonical enum. Its values are Retain, Retire,
  Rehost, Replatform, Refactor, and Repurchase. The historical label Replace is
  accepted only as an input alias and renders as `Repurchase / Replace` where
  compatibility context helps users.
- Versioned `StrategyDefinition` records own the canonical strategy catalogue.
- Each `ModernizationRecommendation` is an immutable child of one
  `AssessmentRun`, generated by deterministic Python from assessment results,
  findings, criterion evidence quality, and immutable snapshot records.
- The recommendation stores evidence IDs plus provenance projections; evidence
  records remain authoritative in the immutable snapshot.
- Assessment trust is mapped to recommendation trust as Ready, Warning, or
  Blocked. Trust qualifies the recommendation; it never rewrites scores.
- SQLite stores recommendation JSON in an additive table with uniqueness on
  run, asset, and recommendation version. The assessment JSON artifact includes
  the same records.
- Recommendation authority is always `RecommendOnly`; execution authority is
  always `None`. The slice exposes no decision-approval or execution command.

## Consequences

### Positive

- One evidence-to-finding-to-recommendation chain is queryable and auditable.
- All six strategies have one reusable representation and comparison model.
- Existing assessment rules remain backward compatible while gaining canonical
  Repurchase semantics.
- Later governed-decision work can reference immutable recommendation IDs.

### Negative and trade-offs

- The local assessment aggregate grows and remains unsuitable for concurrent
  enterprise operation.
- Alternative scores are bounded deterministic decision support, not calibrated
  probabilities or portfolio optimization.
- Existing artifacts without recommendations remain readable but cannot be
  retroactively assigned recommendation evidence.

## Security, reliability, and operations

Only synthetic source records are used in the demo. No credentials or external
tools are introduced. Parameterized SQLite writes and the existing transaction
protect bundle consistency. A persistence or artifact failure rolls back the
run. Execution checks fail closed because no Phase A recommendation can carry
execution authority.

## Compatibility and migration

The schema migration is additive and idempotent. Existing databases gain a
`modernization_recommendations` table; historical rows are untouched. Existing
DataFrame labels remain unchanged, including Replace. Rollback removes Phase A
reads/writes and UI projection; the additive empty table may remain harmlessly.

## Compliance evidence

- Catalogue, alias, deterministic rule, alternative, and model validation tests.
- Missing, conflicting, and low-confidence trust tests.
- Artifact/SQLite agreement and transaction rollback tests.
- Application and data-platform reference scenario tests.
- Unauthorized-execution test and prohibited authority scan.
- Complete regression and Streamlit startup checks.

## Revisit triggers

Revisit when DS-03 exposes an approved durable decision contract, when
recommendations require independent version evolution within one assessment,
or before any tenant-aware or remotely executed workflow consumes them.
